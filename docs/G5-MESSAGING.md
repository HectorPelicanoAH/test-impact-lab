# G5 — Mensajería local

## Diseño y estrategia de validación (antes de implementar)

Alcance: solo G5. RabbitMQ real, `OrderCreated` v1, pedido+outbox en una transacción SQLite, confirmación del publicador, entrega al menos una vez y deduplicación transaccional por consumidor. Notificaciones y preparación ejecutan procesos HTTP separados y bases SQLite separadas; consulta por HTTP, nunca memoria compartida. Dos colas durables independientes con reintento acotado y cola fallida propia. No correo real. Sin políticas de selección/federación G6 ni telemetría G7.

### Testing Strategy

- App: SPA + HTTP + mensajería. Base antes de cambiar: `pnpm test`, **147 tests / 28 archivos** aprobados. Tests legacy Vitest/Playwright se reutilizan con cambios mínimos; conservar login, HTTP de inventario, snapshots G2–G4 y selected/full.
- Infra primaria: Docker Desktop 29.6.1 / Compose 5.2.0 comprobados. Daemon inicialmente detenido; se inició Docker Desktop instalado. Ningún contenedor preexistente. RabbitMQ `4.2.0-management` descargado con digest `sha256:6431bbd0f22df99ace800138399367d7d6181442dfff09feb2795e15d4bd4b7a`. Sin broker real no se declara G5 completada; no reemplazar por mock.
- Node 24.18.0 / pnpm 11.19.0. Cliente AMQP `amqplib` 2.2.0 verificado en npm: Node >=18, tipos propios, sin dependencias transitivas. Persistencia con `node:sqlite` (API experimental en Node 24).
- Unidad/contrato: schema/event ID/correlación; transacción de pedido+outbox; deduplicación y effects atómicos; errores de versión y entrega duplicada. Se incorporan al comando canónico `pnpm test`.
- Integración: RabbitMQ real con namespace único por ensayo; procesos de proveedor/consumidores independientes; publicación duplicada, fallo transitorio/permanente de notificaciones sin bloquear preparación, DLQ y recuperación del publicador después de caída. Esperas por condiciones/HTTP/confirmaciones con plazo máximo, no pausas fijas arbitrarias. Ensayo explícito `pnpm test:messaging` con infraestructura creada/eliminada por el lanzador; sin broker, errores visibles, no falsos PASS.
- Navegador: Playwright existente se conserva. Nuevo recorrido de pedido→consulta preparación/buzón por HTTP en perfil de mensajería, y navegación a evidencias de publicación/suscripción archivadas. Ausencia de Docker no elimina el tier de navegador básico; deja incompleta aceptación de mensajería.
- Aislamiento: puertos efímeros y prefijos únicos en tests; SQLite en temporales, nunca bases del usuario. Solo eliminar contenedor/proyecto/volúmenes creados para el ensayo. Arranque normal usa recursos locales dedicados, sin tocar servidores actuales.
- Grafo: calificadores broker lógico+entorno+exchange+routing key+schema; source/config verificables. Alta/baja de consumidor y routing dinámico deben producir delta/diagnóstico. Compartir broker no enlaza consumidores entre sí. Hasta G6 selección conservadora sobre catálogo disponible.

## Referencias comprobadas

- [RabbitMQ acknowledgements y publisher confirms](https://www.rabbitmq.com/docs/confirms): confirmación de publicación no prueba procesamiento; ACK manual después de persistir efectos; reconexión puede causar duplicados.
- [RabbitMQ dead-lettering](https://www.rabbitmq.com/docs/dlx): reencaminamiento fallido exige considerar seguridad de republicación; este ejemplo confirma explícitamente antes de ACK del original.
- [amqplib API](https://amqp-node.github.io/amqplib/channel_api.html): canales de confirmación, `publish`, `sendToQueue`, `consume`, `ack`, `prefetch` y cierre.

## Implementación y operación

`pnpm dev:events` inicia el broker propio y las siete aplicaciones/procesos del perfil. Requiere Docker en marcha, Node/pnpm indicados y dependencias instaladas. El primer arranque puede descargar la imagen fijada. Frontend: `http://127.0.0.1:5173/orders`; explorador: `http://127.0.0.1:5175`. API pedidos 3001, API demo 3002, inventario 3003, notificaciones 3004, preparación 3005. Si están ocupados, configurar `FRONTEND_PORT`, `DEMO_PORT`, `BACKEND_PORT`, `DEMO_API_PORT`, `INVENTORY_PORT`, `NOTIFICATIONS_PORT`, `PREPARATION_PORT`; el lanzador no detiene servidores existentes. Los tests usan puertos efímeros.

- Broker: RabbitMQ **4.2.0**, versión consultada dentro del contenedor real. Imagen exacta indicada arriba; solo AMQP publicado en loopback/puerto efímero. Credenciales públicas del fixture local `impact` / `impact-local-demo`, nunca usar en producción. Administración no expuesta al host. Límite 768 MiB / 2 CPU; schedulers Erlang acotados. Readiness comprueba handshake AMQP con timeout, no lanza una VM CLI repetidamente durante boot.
- Contrato: [OrderCreated](../packages/api-contract/src/order-created.ts) v1, IDs UUID de evento/correlación, fecha y pedido aceptado validado. `correlationId` es el ID del pedido. [OrderStore](../apps/backend/src/orders/OrderStore.ts) guarda pedido+outbox en transacción SQLite; [publicador](../apps/backend/src/orders/OutboxPublisher.ts) confirma publicación persistente/mandatory antes de marcar salida. Broker caído: pedido persiste, outbox queda pendiente y se reintenta. Sin `BROKER_URL`, publicador deshabilitado y estado explícito `not-enabled`.
- [Topología](../packages/messaging/src/topology.json): exchange directo `orders.events`, routing `order.created.v1`; `notifications.order-created.v1` y `preparation.order-created.v1`, cada una con cola `.failed.v1`. `BROKER_NAMESPACE` prefija exchange/colas para aislar instancias. El grafo registra identidad lógica/entorno declarados, no inventa namespaces observados.
- [ConsumerStore](../packages/messaging/src/ConsumerStore.ts): inbox/event payload + efecto local atómicos en SQLite. Duplicado idéntico no duplica filas; colisión de ID/contenido se rechaza. ACK manual tras efecto duradero, o tras confirmar republicación. Tres intentos máximo para errores de procesamiento; el tercero publica en la cola fallida propia. Los reintentos inmediatos no implementan backoff/DLX/TTL; son republicaciones confirmadas por aplicación. Caídas del broker/conexión se recuperan aparte y no tienen un límite global de tres conexiones.
- Notificaciones almacena un buzón local; preparación almacena un registro `ready`. Funciones de efecto puras: no integrar correo/pagos externos en ellas suponiendo exactamente una vez. Bases independientes por proceso, consultas exclusivamente HTTP (`/orders/:id`). El backend agrega resultados en `/orders/:id/progress`. Un 404 de consumidor significa `pending`; fallo HTTP significa `unavailable`, no mensaje procesado. La pantalla refresca explícitamente con **Refresh processing status**.
- Fallos de demo: `CONSUMER_FAIL_FIRST=1` provoca un fallo inicial; `CONSUMER_FAIL_SKU=failure-widget` provoca fallo permanente de ese SKU. Para limitar el fallo a notificaciones, usar esas variables solo en su proceso; el test real lo hace así. No son reglas del motor de selección.
- Cierre Ctrl+C: detener hijos, retirar solo contenedor/volumen propios y directorios temporales propios. `dev:events` es desechable por defecto, con datos temporales. Un `DATA_DIR` o `INVENTORY_ROOT` proporcionado se conserva. Retener SQLite **no** recupera mensajes ya publicados si se elimina el volumen del broker: para persistencia manual conservar broker y bases. No hay recuperación ante pérdida de disco ni clúster HA. El perfil básico sin broker usa `.impact-data/`, ignorado por Git.

Intentos fallidos corregidos: broker inicial salió durante readiness, sin logs conservados (causa original no demostrada; no afirmar OOM); diagnóstico posterior arrancó. Se cambió readiness a handshake ligero y límites de schedulers, con sucesivos arranques reales correctos. Una llave ausente en lanzador y `expect.poll` no permitido en `beforeAll` se corrigieron. La resolución pnpm de `amqplib` desde bundles falló: se incluyó AMQP en los bundles y se repitió integración sobre ellos. Las comparaciones AST se hicieron estructurales para ignorar formato; se corrigió el selector accesible del test Chromium. El watcher real excedió 5 s bajo 33 workers; aislado pasó y el plazo por condición se amplió a 15 s, sin eliminar su oráculo ni sustituirlo por pausas.

## Seguridad, recursos y límites

- [Scan del paquete añadido](../impact/evidence/g5-cve.json): `amqplib@2.2.0`, sin CVE conocidas según GitHub Advisories en esta ejecución. No certifica toda la aplicación ni la imagen del contenedor.
- `pnpm audit --prod` encontró **1 aviso bajo preexistente**: DOMPurify 3.4.15, [GHSA-p98j-92pf-mc4p](https://github.com/advisories/GHSA-p98j-92pf-mc4p), parche >=3.4.16, transitivo de Monaco. La misma versión está en HEAD anterior a G5. Se deja pendiente fuera del grupo de mensajería; no se afirma auditoría global limpia ni vulnerabilidad remediada.
- Docker Desktop se inició y queda en marcha; la imagen descargada permanece en caché. Contenedores/volúmenes y bases propios de los ensayos se eliminaron; no se usó prune ni se detuvieron servicios ajenos. No hay commit/push del checkout ni despliegue remoto.
- `node:sqlite` sigue experimental en Node 24. No se promete exactamente una vez, HA, reserva de inventario, retención de eventos/datos, backoff de mensajes o autenticación de producción. El runner es de confianza, no sandbox.
- Adaptador acotado a estas formas de código/configuración, no análisis universal de tráfico. Sin telemetría ni cobertura medida. Política conservadora sobre **39 tests login disponibles**; las nuevas suites G5 no están federadas ni seleccionadas por el runner de demo. Eso corresponde a G6, todavía no autorizada.
